# Development data: where it comes from, and what you must not touch

CoOps has two kinds of data and they are governed by opposite rules.

| | what it is | rule |
|---|---|---|
| **Raw** | the provider's HTTP responses, exactly as returned | **frozen.** Never written to during development |
| **Derived** | Bronze, Silver, Gold — everything the pipeline computes | **disposable.** Regenerated per phase, never committed |

Get this backwards and the work stops meaning anything. The reason is in
*[Why the raw tier is frozen](#why-the-raw-tier-is-frozen)* below, and it is not
hypothetical — it happened.

## The rule

> Raw data is fetched from the provider APIs by a **scheduled sync** (#195).
> Development works from a **frozen snapshot** and re-fetches **only** when the
> change under test is the API-fetching layer itself, or the business logic that
> decides what we ask for.

A Silver refactor, a Gold metric, a dashboard change, a phase→main
regeneration: all derive from the snapshot and contact no provider.

## Snapshots

Immutable, checksummed tarballs of the raw tier:

```
~/.local/share/coops/snapshots/
  coops-raw-20260924T023411Z.tar.gz        cache/ only — 12,206 entries, fga-eps-mds
  coops-raw-20260924T023411Z.tar.gz.sha256
```

A snapshot holds **`cache/` only**. Derived layers are deliberately excluded: a
snapshot exists so that two runs months apart see identical input, and freezing
a `data/` tree alongside it invites someone to treat computed output as a
fixture. (The earlier `coops-corpus-*` snapshots do contain `data/`; ignore that
half.)

### Restore

```bash
cd ~/.local/share/coops/snapshots
sha256sum -c coops-raw-20260924T023411Z.tar.gz.sha256   # never skip this
mkdir -p /var/tmp/coops-work && tar -xzf coops-raw-20260924T023411Z.tar.gz -C /var/tmp/coops-work
```

Verify the checksum every time. A corrupted or substituted fixture that is
silently derived from is worse than one that fails to restore, because the
numbers it produces look ordinary.

### Making a new one

Only when the sync has genuinely brought in new upstream data, and deliberately:

```bash
cd /var/tmp/coops-work && tar -czf ~/.local/share/coops/snapshots/coops-raw-$(date -u +%Y%m%dT%H%M%SZ).tar.gz cache
cd ~/.local/share/coops/snapshots && sha256sum coops-raw-<stamp>.tar.gz > coops-raw-<stamp>.tar.gz.sha256
```

New file, new timestamp. **Never edit a snapshot in place** — a fixture that
changes under you is not a fixture.

## Deriving a phase's data

Run the pipeline from a scratch directory, never from the checkout: it reads and
writes `./data` relative to the working directory and will overwrite tracked
files.

```bash
cd /var/tmp/coops-work
uv run --project <repo> coops-bronze --cache
uv run --project <repo> coops-silver
uv run --project <repo> coops-gold
uv run --project <repo> coops-aggregate
uv run --project <repo> coops-registry      # last: it inventories what the others wrote
```

`coops-registry` runs **last and is not optional**. `data/master_registry.json`
and `data/data_catalog.json` are generated by scanning the layers on disk, so
skipping it leaves manifests advertising files that no longer exist.

### Derived data is never committed

Until the phase work is finished, nothing under `data/` reaches any repository —
not a branch, not a PR, not the fork. Phase PRs carry `src/`, `tests/` and docs.

## Why the raw tier is frozen

On 2026-09-24 a regeneration believed to be a pure re-derivation from the local
cache was measured. In 35 minutes it had:

- written **464 entries** into the raw cache
- consumed ~110 REST calls (rate limit 4991 → 4883)

`--cache` means *"use cached data when available"*. On an ETag it **revalidates
over the network and updates the cache as it goes**. So the input was changing
underneath the run.

That is not a performance problem. It means **two phases regenerating "from the
same cache" do not see the same input**, so the second cannot be compared to the
first — and the comparison is the whole purpose of a phase→main regeneration.

### The check this needs, which does not exist yet

There is currently **no offline mode**. `--cache` is a preference, not a
guarantee, so "we are working from the snapshot" is a claim nobody can verify.
#195 tracks a mode where a cache miss or an ETag revalidation **fails loudly**
instead of reaching out.

Until it lands, verify by measurement rather than by intent:

```bash
gh api rate_limit --jq .resources.core.remaining     # before
# ... run the pipeline ...
gh api rate_limit --jq .resources.core.remaining     # unchanged?
find <work>/cache -type f -mmin -30 | wc -l          # must be 0
```

Both, not either. An unchanged rate limit alone does not prove offline operation:
GitHub does not charge 304s against the quota, so ETag revalidation is invisible
to it while still being a network round-trip that rewrites the cache.

## Refreshing from the providers

Fetching new upstream data is a **deliberate act**, not a side effect of running
the pipeline. It belongs to the scheduled sync (#195), which writes into our own
store and produces a new snapshot. If you find yourself re-fetching in order to
test a Silver change, the setup is wrong.

The current corpus is complete as of 2026-09-23: **486 of 486** repositories in
`fga-eps-mds` (after the blacklist/fork filter removes 169), all watermarked,
no truncation. The known gap is member profile fetches, which are unwatermarked
and dominate extraction traffic — #150.
